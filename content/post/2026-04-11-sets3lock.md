## 背景・目的

先週は三日三晩寝込んでしまい非常につらい思いをしたいっちーです。

さて、もう2年近く前になりますが、Amazon S3 が条件付き書き込みに対応しましたね。
昨年9月には条件付き削除にも対応しています。

- [Amazon S3 が条件付き書き込みのサポートを開始](https://aws.amazon.com/jp/about-aws/whats-new/2024/08/amazon-s3-conditional-writes/)
- [Amazon S3 が S3 汎用バケットでの条件付き削除をサポート](https://aws.amazon.com/jp/about-aws/whats-new/2025/09/amazon-s3-conditional-deletes-s3-general-purpose-buckets/)

これの何が嬉しいかと言うと、今までDynamoDBが必要だった場面で、S3だけでカバーできるケースが増えます。

他所の例だと Terraform が有名ですね。
Terraform の S3 backend は多重実行を防ぐために元々は DynamoDB が必要でした。
条件付き書き込みがリリースされてからは多重実行防止の仕組みがS3だけで動くようになりました。
構成がシンプルになって管理するリソースが減るので嬉しいですね。

- [Terraform v1.10 からは S3 Backend の State Lock に DynamoDB が必要なくなる](https://zenn.dev/terraform_jp/articles/terraform-s3-state-lock)

僕も似たような用途で DynamoDB を利用していました。
昔 AWS Lambda と S3 を使ってyumレポジトリーを作ったときです。
yumレポジトリーのメタデータ更新が並列して走るとロストアップデートの可能性があるので、多重実行防止にDynamoDBを利用していました。

- [AWS Lambda + S3 を使ってyumレポジトリを作った](https://shogo82148.github.io/blog/2021/02/21/private-yum-repo-on-s3/)

> - 排他制御
>   - メタデータ更新が並列して走るとロストアップデートの可能性がある
>   - DynamoDB を使った排他的ロックを実装

「今ならDynamoDBなしで実現できるのでは！」というわけで、やってみました。
また、その副産物として [sets3lock](https://github.com/shogo82148/sets3lock) というものができたので紹介します。

- [shogo82148/sets3lock](https://github.com/shogo82148/sets3lock)


## まとめ

自作のyumレポジトリーの排他制御にS3を使用することで、DynamoDB依存を取り除きました。

その副産物として [sets3lock](https://github.com/shogo82148/sets3lock) というものができたので紹介しました。

- [shogo82148/sets3lock](https://github.com/shogo82148/sets3lock)

S3のみで排他制御を行うライブラリーです。
今までDynamoDBを使っていた一部のケースを代替できます。
